# ADR-008: Layered Idempotency and Deduplication

**Status:** Accepted  
**Date:** 2026-11-19

## Context

An order can be submitted more than once because a client may retry after a timeout or lose the HTTP response. RabbitMQ can redeliver an unacknowledged message. The orchestrator can also retry a provider call when the response is delayed or lost.

These are different duplication problems and require separate identifiers.

The system uses three layers:

1. The intake HTTP `Idempotency-Key` identifies a client submission.
2. The orchestrator `businessKey` identifies the business order across saga messages.
3. Provider `Idempotency-Key` values identify side-effecting payment and inventory operations.

Notifications also need deduplication because outcome messages can be delivered more than once.

A single identifier cannot safely cover all these cases. A client submission, a business order, and a payment authorization are different units of work.

## Decision

Use layered idempotency, with each layer protecting a different boundary.

### 1. Intake HTTP idempotency key

The intake service requires an `Idempotency-Key` header. It validates the key and stores the request body hash, HTTP status, and response in `data/idempotency.json`.

When the same key and same payload are submitted again, intake returns the previously stored response instead of publishing another order.

If the same key is reused with a different payload, intake returns HTTP 409 with `idempotency_payload_mismatch`.

The in-flight map also detects concurrent requests using the same key. A concurrent request with the same payload receives `idempotency_conflict`, while a different payload receives `idempotency_payload_mismatch`.

**Failure caught:** A client times out after submitting an order and retries the same HTTP request. Without this layer, the retry could create another correlation ID and publish another order.

### 2. Saga business-key deduplication

Intake creates the business key as:

`<source>:<orderId>`

It includes this key in the RabbitMQ message headers. The orchestrator persists a mapping from `businessKey` to the original `correlationId` in its saga store.

When a different correlation ID arrives with a business key already registered, the orchestrator records the new saga as `duplicate`, publishes a duplicate outcome, and acknowledges the message. The outcome includes `duplicateOf` so the original order can be identified.

**Failure caught:** A client or upstream system submits the same business order with a new idempotency key. Intake sees a new submission, but the orchestrator still recognises the already-registered business order.

The business key represents the same business order, not every future purchase by the same customer. A genuinely new order must have a new order ID and therefore a new business key.

### 3. Provider idempotency keys

The orchestrator sends operation-specific keys to providers:

- `authorize:<businessKey>` for payment authorization.
- `reserve:<businessKey>` for inventory reservation.
- `refund:<businessKey>` for payment compensation.
- `release:<businessKey>` for inventory compensation.

The shared provider engine scopes a stored key by operation name. If the same operation and key already produced an effect, it returns the stored response without creating another effect. Concurrent calls with the same key wait for the in-flight call to finish.

A failed call that produced no effect does not store a successful result, so a later retry can be processed again. This distinction matters when a provider times out after performing an effect: a retry must not charge or reserve twice.

The mock provider engine keeps these stored results in its in-memory state; this is not a durable external payment-provider ledger.

**Failure caught:** A payment authorization succeeds at the provider, but the response is lost before the orchestrator receives it. A retry with the same key returns the stored result without creating a second authorization effect.

### 4. Notification deduplication

The notifier separately stores processed correlation IDs in `data/processed-ids.json`. If an outcome for an already-processed correlation ID is delivered again, the notifier acknowledges it without sending another notice.

This is necessary because message delivery is at-least-once: the same event can be received again after a retry or consumer interruption.

## Alternatives considered

### One deduplication layer only

Rejected because each layer protects a different boundary. Intake idempotency cannot detect a repeated business order submitted with a new key. Business-key deduplication cannot prevent a provider from applying the same side effect twice after a lost response.

### Correlation ID as the only key

Rejected because a new submission normally receives a new correlation ID. It would therefore fail to recognise the same business order arriving as a separate message.

### Rely only on RabbitMQ delivery guarantees

Rejected because message acknowledgements and redelivery do not prevent duplicate business effects. At-least-once delivery requires consumers and providers to handle repeated messages safely.

## Consequences

- Retried HTTP submissions with the same key and payload reuse the stored response.
- Reusing an intake key with a different payload is rejected with HTTP 409.
- Repeated business orders are detected even when they arrive with different correlation IDs.
- Provider retries reuse operation-specific keys to avoid repeating successful mock payment or inventory effects.
- Repeated notification outcomes do not generate another notice for an already-processed correlation ID.
- RabbitMQ delivery remains at-least-once. The design prevents duplicate effects at the implemented boundaries; it does not provide exactly-once message delivery.
- Intake and notifier deduplication records are persisted locally, while mock provider idempotency results are in memory. A real deployment would need durable provider-side idempotency records and appropriate persistence and recovery guarantees.
- The business key must represent a genuinely unique order. Reusing an order ID for a new purchase can cause that purchase to be treated as a duplicate.
