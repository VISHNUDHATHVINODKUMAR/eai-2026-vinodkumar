# ADR-009: Wire-Tap Distributed Tracing

**Status:** Accepted  
**Date:** 2026-11-19

## Context

An order passes through several services: intake, orchestrator, mock providers, and notifier. Looking at the logs of each service separately does not provide a complete view of one order or clearly show which operation caused the next operation.

Operators need to follow an order using one correlation ID, inspect the sequence of service operations, identify failures and timeouts, and understand retry attempts and compensation steps.

The system therefore needs a separate trace stream that records the progress of an order without replacing the business messages exchanged by the services.

## Decision

Use the **Wire Tap** integration pattern. Services create trace-hop records and publish them to the RabbitMQ `trace.events` exchange. The observer consumes the trace stream through `trace.store` and writes each event to `trace-store.jsonl`.

The shared implementation is in `shared/trace.js`.

Each hop contains a unique `hopId`, the order's `correlationId`, a `causationId`, service and operation names, an attempt number, a status, and timestamps. The completed record also contains `durationMs`. A message ID or additional detail is included when available.

`startHop()` creates the hop and its start timestamp. `finishHop()` adds the finish timestamp, duration, and final status, then publishes persistent JSON to `trace.events`.

Publishing is not fire-and-forget. `finishHop()` waits for the RabbitMQ publisher confirmation callback before returning the completed record. A publishing error rejects the operation awaiting it. This makes trace publication visible to the caller, but it also means tracing can affect business processing when the broker is unavailable.

### Correlation and causation

The `correlationId` remains the identifier for the complete order. Each new hop receives a unique `hopId`. The next operation uses the previous hop's ID as its `causationId`, creating a linked sequence.

Intake starts the trace with a receive hop, followed by translation and publication hops. The orchestrator records message consumption and links subsequent saga and compensation operations to the previous hop. Provider calls also receive correlation and causation identifiers in their request headers.

The orchestrator calculates the retry attempt from RabbitMQ's `x-death` history. The original message headers are not rewritten by a negative acknowledgement, so a redelivered message can retain its previous causation ID. The new consume hop links to that incoming causation ID and records the new attempt number. This preserves the available causal relationship while making each consumption a distinct hop.

### Observer and trace storage

The observer consumes `trace.store`, appends each valid event to `trace-store.jsonl`, and acknowledges the message after the append succeeds. If parsing or storage fails, it rejects the message without requeueing it.

The observer exposes `GET /trace/:correlationId`, which reads stored events for the requested correlation ID and sorts them by start time. Its health endpoint reports whether its RabbitMQ connection and trace consumer are available.

If the observer is unavailable while RabbitMQ remains available, trace events can accumulate in the `trace.store` queue until the observer consumes them again. This depends on the broker retaining the queued messages. The observer implementation does not automatically reconnect after a connection closes; it reports degraded health instead.

## Alternatives considered

### Scatter-gather

Rejected because the services do not need to wait for several independent responses to complete one business operation. Trace events are observations of work already taking place, not responses that must be combined.

### OpenTelemetry

OpenTelemetry would provide a standard instrumentation and collection ecosystem. It was not selected for this capstone because the implemented requirement is a small RabbitMQ-based trace stream with correlation and causation links. Introducing a separate collector and instrumentation dependency would add deployment and configuration complexity.

### Fire-and-forget trace publishing

Rejected because a service could report an operation as complete without knowing whether its trace event had been accepted by RabbitMQ. The current implementation waits for publisher confirmation, making publication failures visible to the calling operation.

## Consequences

- Operators can query a complete stored trace by correlation ID instead of manually joining unrelated service logs.
- Unique hop IDs and causation IDs make the sequence of operations and compensation steps easier to follow.
- Trace events are persistent RabbitMQ messages, and the observer acknowledges them after appending them to its local JSONL file.
- Trace publication adds broker traffic, serialization work, and a publisher-confirmation wait to instrumented operations.
- A broker outage can cause trace publication to fail and can therefore affect business processing that awaits `finishHop()`.
- An observer outage does not immediately prevent the broker from accepting trace events, provided RabbitMQ remains available and the relevant queues retain their messages. The observer itself does not implement automatic reconnection.
- If the broker cannot accept or confirm a trace event, the event may not be recorded. The implementation does not provide a separate durable local trace outbox.
- The observer's JSONL file is local storage. A production deployment would need explicit retention, backup, access-control, and recovery policies.
- The trace is an operational diagnostic record, not a replacement for the saga state store or an independent audit ledger.
