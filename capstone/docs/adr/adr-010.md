# ADR-010 — Manual Recovery of Stuck Sagas

**Status:** accepted  
**Date:** 2026-11-19

## Context

The orchestrator persists saga state in its local store. A saga can be left in `processing` if the orchestrator process stops unexpectedly while an order is being processed. External provider operations may already have taken effect, so blindly starting the saga again could repeat work or produce inconsistent business results.

Each saga records its owner run ID. A new orchestrator process has a different `RUN_ID`. The system therefore needs to identify unfinished sagas owned by an earlier process and make them visible for deliberate recovery.

A crash can occur between a provider operation and saving the updated saga state. Consequently, the persisted list of completed steps may not always prove whether an external side effect occurred. Recovery requires checking the recorded saga history and relevant provider state before deciding what to do.

## Decision

The orchestrator uses `markPreviousRunSagas()` to detect unfinished work. After the configured `SAGA_STUCK_AFTER_MS` delay (default 10,000 milliseconds), it scans persisted sagas. A saga is eligible when its state is `processing`, its owner differs from the current `RUN_ID`, and it has no recorded outcome.

For each eligible saga, the orchestrator records `stuckAt`, saves the store, creates a `saga.stuck` trace hop, and publishes an outcome with state `needs_attention`. It does not automatically restart the saga.

Operators can inspect stuck sagas through `GET /sagas/stuck` and request recovery through `POST /sagas/:correlationId/compensate`.

The compensation endpoint:
- Returns `404` when the saga does not exist.
- Returns `409` if compensation is already running or the saga is not in `needs_attention` or `compensation_failed`.
- Saves an operator-compensation record with status `running` before starting.
- Calls the existing `compensate()` function and records the final response and status.
- Returns the previously saved response when a saga is already compensated, making a repeated successful operator request safe at the endpoint level.

Compensation reverses completed operations in reverse order. If inventory was completed, it attempts `inventory_release`; if payment was completed, it attempts `payment_refund`. Already successful compensations are skipped. B2B orders skip the payment step, so they do not require payment refunds from this compensation list.

The operator must inspect the saga's completed and compensated steps, trace history, failure information, and relevant provider state before requesting compensation. The endpoint is not a substitute for that investigation.

## Alternatives considered

**Automatically resume unfinished sagas.** This could improve recovery time, but it would require reliable knowledge of which provider operations completed before the crash. A crash between a provider side effect and saving the saga could cause an operation to be repeated. Safe automatic resumption would require carefully designed idempotent activities, durable step-level execution records, and reconciliation with provider state. The current implementation does not provide enough evidence to resume every interrupted saga safely.

**Mark every unfinished saga as failed.** This is simpler, but it hides the important distinction between a business failure and an interrupted process whose external side effects may be uncertain. `needs_attention` makes the recovery requirement explicit.

**Use Temporal for durable workflow execution.** Temporal could persist workflow history and replay workflow execution after worker restarts, replacing much of the custom previous-run detection and recovery coordination. It would require adopting Temporal infrastructure, defining workflows and activities, migrating saga state and operational procedures, and ensuring provider activities remain idempotent. Temporal would not make external provider calls exactly-once automatically.

## Consequences

The system avoids blindly repeating unfinished saga steps and gives operators an explicit recovery path. The trade-off is that recovery is not automatic and requires investigation and operator action.

The detection rule can produce false positives: a saga owned by a previous process may have completed an external operation just before the process stopped, even though that step was not saved locally. The delay also means detection is not immediate. The configured threshold is a practical detection delay, not proof that a saga is permanently unrecoverable.

Before compensating, the operator must inspect the saga status, completed steps, successful compensations, trace events, failure details, and provider state where available. The operator should verify whether inventory was reserved and whether payment was captured before triggering release or refund. B2B orders do not use the payment step.

The implementation remains dependent on the local persisted saga store and custom recovery logic. A future Temporal migration could provide durable workflow history, replay, and workflow timers, but provider-side idempotency, compensation design, and human review of uncertain external effects would still be necessary.
