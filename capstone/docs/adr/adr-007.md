# ADR-007: Event-Driven Saga Orchestration

**Status:** Accepted  
**Date:** 2026-11-19

## Context

The intake service accepts orders over HTTP, while the orchestrator coordinates the multi-step order workflow. These responsibilities need to remain separate so that accepting an order does not require the orchestrator to complete its work during the same HTTP request.

A synchronous HTTP call from intake to orchestrator would couple order acceptance to orchestrator availability and response time. It would also make transient failures harder to recover from.

The workflow must support asynchronous processing, retries, duplicate delivery, correlation across services, and publication of a final outcome.

## Decision

Use RabbitMQ and an event-driven Saga pattern.

1. The intake service validates and stores the incoming order, then publishes a persistent message to `orders.exchange`.
2. The orchestrator consumes messages from `saga.queue` and coordinates the workflow steps.
3. The orchestrator uses `correlationId` to identify the saga and `businessKey` to identify the business order. Correlation and causation identifiers are propagated through the workflow and trace events.
4. The orchestrator limits concurrent message delivery using `channel.prefetch(CONCURRENCY)`. The default concurrency is 5 and can be configured with `SAGA_CONCURRENCY`.
5. The orchestrator persists saga state and terminal outcome information before publishing the outcome to `orders.outcome`.
6. The incoming message is acknowledged after successful processing. Failures use the configured retry and dead-letter mechanisms rather than silently discarding work.
7. The intake `GET /orders/:correlationId` endpoint obtains the latest saga state from the orchestrator when it is available. If the orchestrator cannot be reached, intake returns its locally stored order information with state `accepted`.

The orchestrator stores terminal outcome information before publishing it. This supports recovery when a message is redelivered after a failure: the saved outcome can be published again rather than requiring the workflow to be treated as a new order.

**State-transition limitation:** The current implementation assigns `saga.state = state` when saving an outcome. It does not enforce a formal monotonic state-transition rule. Therefore, the implementation does not guarantee that a saga can never move backwards. The intake fallback to `accepted` when the orchestrator is unavailable is also not proof that the saga itself has returned to that state; it is a fallback response.

## Alternatives considered

### Synchronous HTTP orchestration

Rejected because order acceptance would depend on orchestrator availability and response time. It would also make asynchronous retries and recovery more difficult.

### Direct database sharing

Rejected because it would couple intake and orchestrator to the same persistence model and allow one service to depend on another service's internal data structures.

### Fully asynchronous messaging

Accepted. RabbitMQ allows intake and orchestration to operate independently and provides message acknowledgement, retry, and dead-letter mechanisms.

## Consequences

**Positive consequences**

- Intake can accept and persist an order without waiting for the complete saga.
- The orchestrator can process orders asynchronously.
- RabbitMQ supports controlled message delivery, retries, and dead-letter handling.
- Correlation and causation identifiers make it possible to follow an order across services.
- Persisting terminal outcomes before publication improves recovery after redelivery.
- Saga concurrency can be controlled through configuration.

**Trade-offs and limitations**

- Order status may not be immediately available after intake accepts an order.
- The intake status endpoint depends on the orchestrator for the latest saga state.
- When the orchestrator is unavailable, intake returns the locally stored `accepted` state, which may not reflect the actual saga state.
- Message delivery and outcome publication can occur more than once, so consumers must handle duplicates safely.
- The current implementation does not enforce monotonic saga state transitions. A future improvement should validate allowed transitions and prevent a terminal state from being overwritten by an earlier state.
