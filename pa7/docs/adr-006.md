# ADR-006 — Using Temporal for the Checkout Saga

**Status:** Accepted  
**Date:** 2026-11-09

## Context

In PA6, I managed the checkout process using my own code. I had to handle retries, timeouts, failures and refunds manually.

The main problem was what happened if the application crashed in the middle of an order. It was difficult to know which steps had already finished and which needed to run again.

## Decision

I decided to use Temporal to manage the checkout workflow.

I split the process into four activities: payment, inventory, shipping and notification. These are implemented in `worker/src/activities/index.ts`, while the workflow is in `worker/src/workflows/checkout.ts`.

Temporal handles retries and recovery. I also added compensation so that payment can be refunded and inventory released if a later step fails.

## Alternatives considered

I could have kept the PA6 approach and added my own recovery mechanism, but that would mean writing and maintaining more code.

I also considered retrying every failure, but that would waste time on permanent errors such as a declined payment.

Temporal seemed like the better choice because it already provides workflow history, retries and recovery.

## Consequences

The biggest advantage is that a worker can restart without losing the workflow's progress.

However, I now have to run and monitor Temporal as well as my other services.

Retries can also cause the same external request to happen more than once. For example, shipping may be called twice after a crash. This means external services still need idempotency protection.

## What the engine took over

- **Workflow progress:** In PA6, my code tracked the saga steps. In PA7, Temporal stores the workflow history.
- **Retries:** I previously had to manage retries myself. Temporal now handles them using the configured retry policy.
- **Timeouts:** Temporal handles activity timeouts using `startToCloseTimeout`.
- **Recovery:** In PA6, I needed to think about what happened after a crash. In PA7, Temporal can resume the workflow when a worker comes back.
- **Execution history:** Instead of tracking everything manually, I can use the Temporal UI to see what happened at each step.
