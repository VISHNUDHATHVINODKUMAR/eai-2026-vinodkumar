# ADR-006: Use Temporal to Manage the Checkout Saga

**Status:** Accepted  
**Date:** 2026-11-09

## Context

In PA6, I implemented the checkout saga in my own orchestrator. It called payment, inventory, shipping and notification services in sequence. I also had to manage timeouts, retries, compensation and recovery.

A major risk was an application failure during checkout. The orchestrator needed to know which steps had completed before it could safely continue or compensate them. Maintaining this recovery logic myself made the implementation more complex.

## Decision

I decided to use Temporal to manage the checkout workflow.

I separated the workflow from its activities. The activities contain the calls to external services, while `worker/src/workflows/checkout.ts` controls their order.

The workflow runs four activities sequentially:

1. Authorize payment.
2. Reserve inventory.
3. Create shipment.
4. Send notification to the customer's email address.

The total amount is calculated using integer cents to avoid floating-point rounding problems. It is then formatted as a two-decimal amount.

Normal activities use a 60-second start-to-close timeout. Shipping uses a shorter 5-second timeout so a slow shipping request can trigger compensation without applying that short timeout to every activity. Both activity proxies retry up to three attempts with exponential backoff.

If a later activity fails, the workflow compensates completed steps in reverse order: release inventory, then refund payment. A payment failure does not require compensation because no earlier step has completed. If compensation fails, the workflow returns `failed` with code `compensation_failed`. A timeout is recorded separately with code `timeout`.

Temporal stores workflow history and supports recovery after a worker restart. HTTP request idempotency remains a separate responsibility of the API and its persistent store; Temporal does not replace that mechanism.

## Alternatives considered

I could have kept the PA6 orchestrator and maintained recovery, retries and compensation in my own code. PA6 already uses compensating endpoints for inventory release and payment refund. This avoids adding Temporal, but requires maintaining more recovery and retry logic myself.

I also considered a choreography approach, where services coordinate through events. This would reduce central orchestration but make the sequence and compensation behavior harder to follow and test.

I chose Temporal because its workflow history, retry policies and recovery support make the checkout process easier to manage. The cost is an additional Temporal service and the need to operate and monitor it.

## Consequences

The main benefit is that a worker can restart without losing the workflow's recorded progress. However, external activities can be attempted more than once after failures. For example, a shipping request may be retried. External operations therefore still need idempotency protection.

A fifth checkout activity would require updating the workflow sequence and deciding whether it needs compensation. Two requests racing with the same order ID must still be handled by the API's idempotency checks. If the API process is killed while a request is `in_progress`, the persistent request state and recovery behavior must be considered separately from Temporal's worker recovery.

I accept the extra Temporal infrastructure and the need to make external activity calls safe to retry.

## Evidence

In my test run, the PA7 public suite passed all 13 tests, including the slow-shipping timeout and worker-restart recovery cases. The PA6 public suite passed all 12 tests, covering sequential execution, compensation, idempotency and persistence after an orchestrator restart.

The Spectral contract check reported: `No results with a severity of 'error' found!` The PA6 TypeScript check, `npx tsc --noEmit`, completed without errors.

These results support the decision to use Temporal for workflow coordination while retaining separate API-level idempotency and compensation responsibilities.
