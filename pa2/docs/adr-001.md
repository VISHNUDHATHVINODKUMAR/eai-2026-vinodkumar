# ADR-001 — Durable queue, publisher confirms, manual ack, and correlationId propagation for PA2

**Status:** accepted
**Date:** 2026-09-18

## Context

Four separate failure modes forced four separate decisions in this pipeline.

A non-durable queue does not survive `docker restart pa2-rabbitmq` — the
queue itself disappears, not just its contents, so every message sitting in
it is gone regardless of whether the message was marked persistent. I
verified this by watching `02-broker-restart-survives.test.ts`: with
`durable: true` set on both `connectProducerChannel` and
`connectConsumerChannel`, a confirmed message published before the restart
was still present afterward and the consumer picked it up once it
reconnected.

Publisher confirms decide what a `202` from `POST /publish` actually
promises. The naive version — call `channel.publish()` and respond `202`
immediately — looks correct and passes almost every test, because
`channel.publish()` returns a boolean synchronously whether or not the
broker has actually accepted the message. `04-publisher-confirms-prevents-
loss.test.ts` is the one built to catch this: publishing a batch with
`X-Publish-Mode: fire-and-forget` (no `persistent: true`, no confirm
callback) and then killing the broker lost messages that had already
received a `202`. The same batch published in the default confirmed mode —
`persistent: true`, and not resolving until the confirm callback fires —
lost nothing across the same restart.

Manual ack decides what happens to a message that is mid-write to
`received.jsonl` when the consumer process dies. If `channel.ack(msg)` runs
before `fs.promises.appendFile`, a crash in that gap loses the message
permanently, with RabbitMQ believing it was delivered and removing it from
the queue. I put the ack after the write in `handleMessage` specifically to
avoid that window.

correlationId propagation is not satisfied just because a string shows up
somewhere in the log. It has to survive a specific path: the client's
`X-Correlation-Id` header (or a generated UUID if absent) → the AMQP
message's `correlationId` property → the `correlationId` field of the JSON
line in `received.jsonl`. Putting it in the message body instead of the
AMQP property would work for the happy path but breaks the moment you want
to inspect or route on it without deserializing the payload — the property
exists precisely so the broker and any consumer can see it without parsing
the body.

## Decision

`connectProducerChannel(url, queueName)` opens a `ConfirmChannel` (not a
plain `Channel`) via `connection.createConfirmChannel()`, and asserts the
queue with `durable: true`. Using a confirm channel here is what gives
`publishMessage` its confirm callback later.

`publishMessage` has two branches, controlled by `options.mode`. In
`"confirmed"` mode (the default), it sets `persistent: true` in the publish
options and wraps `channel.publish()` in a `Promise` that only resolves
inside the confirm callback — so the function does not return until the
broker has acknowledged durable receipt. In `"fire-and-forget"` mode, it
calls `channel.publish()` with no `persistent` flag and resolves
immediately with no callback, deliberately reproducing the unsafe path.

`connectConsumerChannel(url, queueName)` opens a plain `Channel`, asserts
the same queue name with `durable: true` (must match the producer's
declaration exactly), and sets `channel.prefetch(1)` so RabbitMQ only hands
this consumer one unacked message at a time.

`handleMessage(channel, msg)` reads `msg.properties.correlationId` directly
— trusted as-is, since the producer already validated the header format
before ever publishing — parses the message body, appends a JSON line
(`{ correlationId, receivedAt, payload }`) to `received.jsonl` with
`appendFileSync`, and only then calls `channel.ack(msg)`.

## Alternatives considered

The most tempting alternative was relying on `channel.publish()`'s return
value (a boolean) as the sole backpressure/success signal, skipping the
confirm channel and callback entirely. This is what most naive amqplib code
does, and it is close enough to correct that it's worth explaining why it
still isn't: that boolean only reports whether the channel's local write
buffer has room, not whether the broker has durably stored the message.
`04-publisher-confirms-prevents-loss.test.ts` exists specifically because
this alternative passes every other test in the suite while still losing
messages on a real restart.

I also considered acking before writing to `received.jsonl`, since it
simplifies the function (no ordering to worry about, no window where a
crash costs a message twice-processed on retry). I rejected it because the
cost of the two failure modes is not symmetric: acking early risks silent,
permanent message loss; writing early and acking late risks only a
harmless duplicate line in `received.jsonl` if the process dies between the
two (since the message is redelivered and reprocessed, not lost).

Finally, I kept the assignment's named RabbitMQ user (`eai`/`eai-pa2`)
rather than falling back to `guest`/`guest`. The README calls this out
directly: `guest` logins are loopback-only by default, so management-API
calls made from the host (via the mapped `15673` port) would silently fail
even though AMQP itself kept working — exactly the kind of bug that looks
fine until you check the one thing that exposes it.

## Consequences

Manual ack with `prefetch(1)` means this consumer processes messages
strictly one at a time. If it's slow, or received.jsonl's disk fills up,
the queue backs up safely (demonstrated in `03-consumer-stopped-
accumulates.test.ts`) rather than dropping messages — but throughput is
capped at whatever single-threaded append-then-ack can sustain, and nothing
here parallelizes consumption.

Running two instances of this consumer against the same queue would work
correctly without code changes — RabbitMQ round-robins deliveries across
consumers on the same queue, and `prefetch(1)` plus manual ack means each
message still only gets processed once. The cost is that message ordering
across the two instances is no longer guaranteed, even though ordering
within a single consumer's stream is.

A very large message body (order of 100MB) is not handled specially
anywhere in this pipeline — `JSON.parse` and `JSON.stringify` both run
synchronously on the full buffer, so a message that large would block the
consumer's event loop for the duration and could stall every other message
behind it in the same process, since there's no back-pressure or
size-based rejection on either the producer or consumer side.

If RabbitMQ's own disk fills up, durable queues stop accepting new
publishes rather than silently dropping them — the confirm callback would
simply never fire, and `publishMessage` would hang until the broker frees
space or the request times out. That's the correct failure mode for a
system this size, but it means a full disk on the broker degrades directly
into unresponsive `POST /publish` calls with no distinct error surfaced to
the caller.
