# ADR-004 - Header correlation id, DLX retry and a file-backed duplicate check

**Status:** accepted
**Date:** 2026-10-12

## Context

An order has to reach payment, inventory and notification, and any of them can be down. Delivery is at-least-once, so the same order can arrive twice. I had to decide where the correlation id goes, how many retries to allow, how notification-service avoids logging an order twice, and what should never be retried.

## Decision

- **Correlation id in a header** (`headers.correlationId`), created in order-service with `crypto.randomUUID()` and copied onto every result event. It is not in the body, because the canonical schema has `additionalProperties: false`.
- **Three attempts, about one second apart** (`MAX_RETRIES=3`, `x-message-ttl: 1000`). After the third failure the message goes to `orders.dlq.exchange` with an `originQueue` header. I kept the scaffold's retry/DLQ block unchanged.
- **Duplicates caught with a file.** notification-service checks the correlation id against `/data/processed-ids.json` first. If it is there, it acks, logs "duplicate skipped" and does not touch `notification.log`.
- **Permanent failures are not retried.** Invalid JSON (a `SyntaxError` inside the try block) goes to `orders.invalid.exchange` with its original bytes and is acked. In notification-service a missing correlation id is also permanent.
- **Replay** reads `orders.dlq` and republishes each message to `orders.return.exchange` with `originQueue` as the routing key, using `withoutRetryHistory` to drop `x-death`. It acks after publishing.

## Alternatives considered

- **In-memory Set for duplicates:** rejected, because `docker compose restart notification-service` wipes it and a redelivered order would be logged again.
- **Replaying through `orders.exchange`:** rejected, because the fanout would send the order to all three consumers.
- **`nack` with requeue:** rejected, because it loops with no delay and never gets an `x-death` header.
- **Retrying invalid JSON:** rejected, because it fails the same way every time and ends up in the DLQ for nothing.

## Consequences

Tracing one order across services is easy, and one failing consumer does not hold up the others. The costs I accepted:

- Three attempts at one second is tight, so a slow but healthy service would end up in the DLQ, and nothing alerts anyone until replay is called.
- If notification-service dies between writing the log line and saving the ids file, that order is logged again after the restart. I preferred a rare duplicate over a lost notification.
- The ids file is not safe with two replicas of notification-service.
- Only notification-service guards against duplicates. Payment and inventory would repeat the work.
- Replay publishes first and acks second, so a crash in between replays the message again. A DLQ message without `originQueue` would be lost, because an empty routing key matches no queue.
- order-service checks only a few fields, not the full schema, and keeps orders in memory.
