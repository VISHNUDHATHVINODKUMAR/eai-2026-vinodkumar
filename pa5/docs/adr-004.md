# ADR-004 - Header correlation id, DLX retry and a file-backed duplicate check

**Status:** accepted
**Date:** 2026-10-12

## Context

Before I wrote notification-service, the RabbitMQ queue list showed 4 orders waiting in `notifications.queue`. `payment.results` and `inventory.results` each held 4 result events, and `notification.results` held none. After I wrote it, `notification.log` had four lines with four different correlation ids, all for the same order, `WEB-2026-002`. So every `POST /orders` is a new unit of work, even when the order content is identical. That forced three decisions: where the correlation id goes, how many retries to allow, and what should never be retried.

## Decision

- **Correlation id in a header.** order-service creates it with `crypto.randomUUID()` and sets `headers.correlationId` when it publishes. Every consumer copies it onto its result event. It is not in the body, because the canonical schema has `additionalProperties: false`.
- **Three attempts, about one second apart** (`MAX_RETRIES=3`, `x-message-ttl: 1000` on the retry queues). `getRetryCount` reads the `x-death` header. After the third failure the message goes to `orders.dlq.exchange` with an `originQueue` header. I kept the scaffold's retry/DLQ block unchanged.
- **Processed means the id is in a file.** `loadProcessedIds` and `saveProcessedIds` in notification-service read and write `/data/processed-ids.json`. If the id is already there, the consumer acks, logs "duplicate skipped" and does not touch `notification.log`.
- **Permanent failures are not retried.** A body that is not valid JSON (a `SyntaxError` inside the try block) goes to `orders.invalid.exchange` with its original bytes and is acked. In notification-service a missing correlation id is also permanent, because the message can be neither traced nor deduplicated.
- **Replay** (`POST /dlq/replay`) reads `orders.dlq` with `channel.get` and republishes to `orders.return.exchange` with `originQueue` as the routing key, so only the failed consumer gets it. `withoutRetryHistory` drops `x-death`, so the message gets a fresh three attempts. The ack comes after the publish.
- **Input check.** `validateOrder` in order-service returns a 400 for a body without a string `orderId`, a `customer.email` and a non-empty `items` array.

## Alternatives considered

- **In-memory Set for duplicates.** It is less code, but `docker compose restart notification-service` wipes it, so an order redelivered after a restart would be logged a second time.
- **Replaying through `orders.exchange`.** It saves nothing in code, and the fanout would send the order to all three consumers, so payment and inventory would repeat work they already did.
- **`nack` with requeue.** It needs no retry queue, but the message comes straight back, can loop forever, and never gets an `x-death` header, so the retry count never grows.
- **Retrying invalid JSON.** It needs no classification code, but it fails identically each time, wastes three attempts, and puts a message in the DLQ that replay can never fix.

## Consequences

Tracing one order across the three services is easy now, and one failing consumer does not hold up the others. The costs I accepted:

- Three attempts at one second is tight. A slow but healthy service would end up in the DLQ, and nothing alerts anyone until replay is called.
- In notification-service the order is: write the log line, add the id, save the file, ack. If the container dies between the log line and the file save, that order is logged again after the restart. I accepted a rare duplicate over a lost notification.
- The ids file is not safe with two replicas of notification-service, because both could read it before either writes.
- Only notification-service guards against duplicates. A replayed or duplicated message that reaches payment or inventory is processed again.
- Replay publishes first and acks second, so a crash in between replays the message again. A DLQ message without `originQueue` would be published with an empty routing key, match no queue, and be lost.
- order-service checks only a few fields, not the full schema, and keeps orders in memory, so `GET /orders/:id` forgets everything on restart.
