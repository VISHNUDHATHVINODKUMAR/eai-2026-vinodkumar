# ADR-000 — Ingest the legacy order export by parsing raw bytes, not by trusting a text encoding

**Status:** accepted
**Date:** 2026-09-13

## Context

The order export is fixed-width, encoded in CP1257, and column-aligned with
trailing space padding. The customer master is a separate file, UTF-8,
semicolon-separated. Two encodings inside one integration, with nothing in
either file that announces which one applies — you have to know it in advance
or guess wrong silently.

Reading the orders file with `readFileSync(path, "utf8")` does not throw. It
returns a string the same length, with the column boundaries still intact, so
every downstream slice still "works" — it just corrupts the Latvian
diacritics. `Bērziņš` becomes garbage, `Šmite` becomes garbage, and there is
no exception anywhere to point at the mistake. The report still gets written,
with plausible-looking rows, wrong content. That is the specific danger the
assignment is built around: the failure is silent and downstream of decoding,
not visible in the line you got wrong.

The other three traps were similarly quiet:

- `amount` uses a comma decimal separator (`45,20`) and is meant to survive as
  a string. Routing it through `parseFloat` drops trailing zeros (`45.20` →
  `45.2`) and quietly turns `7800,00` into `7800` — a loss you would not
  notice reading the JSON unless you already knew to look for the missing
  digit.
- Line 6 of the order file is truncated (26 characters instead of 77). It has
  to be rejected with its line number and reason, not skipped with a bare
  `continue` — a silent skip and a bad throw both destroy information, just
  in opposite directions.
- `ORD-0004` carries a negative amount. It is a refund, and it is real money;
  treating "negative" as "invalid" and filtering it out would be as wrong as
  the encoding bug, just less visible.

## Decision

`decodeOrderFile` reads the orders file as a `Buffer` and decodes it with
`new TextDecoder("windows-1257")` — no `iconv-lite`, since `TextDecoder`
already knows the label. The customer CSV is read separately with plain
`utf8`, because it genuinely is UTF-8; the two files are decoded differently
on purpose, not by oversight.

`ingest()` splits the decoded order text into lines, and for each line checks
`line.length === ORDER_LINE_LENGTH` (77) before touching it. A line that
fails this check goes into `rejected` with its 1-based line number and a
reason string; it is never thrown on and never silently dropped. Only lines
that pass the length check are sliced by fixed column position
(`ORDER_LAYOUT`) into `orderId`, `customerId`, `customerName`, `orderDate`,
`amount`, and `currency`, each `.trim()`-ed to drop the padding.

`toIsoDate` converts `DD.MM.YYYY` to `YYYY-MM-DD` with a plain string split
and reassembly — no `Date` object, so there's no ambiguity about day/month
order and no timezone attached to a value that never had one.

`toDecimalString` does a single `.replace(",", ".")` on the trimmed amount
field and returns it as a string all the way through the pipeline. `amount`
is typed as `string` in the `Order` interface specifically so nothing
upstream or downstream can accidentally coerce it to a `number` and lose
precision.

`parseCustomers` skips the CSV header row, then splits each remaining line on
`;` into a `Map<customerId, fullName>`. `unmatchedCustomers` is the set
difference between that map's keys and the `customerId`s that appear on
accepted orders — computed after rejection, so a customer whose only order
was the truncated line 6 would correctly still count as unmatched.

## Alternatives considered

**`iconv-lite` for the encoding.** Rejected — not just because the assignment
forbids it, but because it's unnecessary: `TextDecoder` in the Node standard
library already recognizes `"windows-1257"` as a label. Adding a dependency
here would hide the actual lesson, which is that you have to know and state
your encoding, not that decoding CP1257 is hard.

**Parsing the order line with a regular expression instead of slicing by
column.** Rejected. A regex over a fixed-width record either has to encode
the exact column widths anyway (in which case it's strictly more fragile than
slicing, since a single off-by-one in the pattern silently misaligns every
field after it) or it tries to split on whitespace, which breaks immediately
because customer names contain spaces.

**Storing `amount` as a `number` and formatting back to two decimals on
output.** Rejected. Even if formatting on output is careful, the value
spends its life in memory as a float, and any computation done on it before
output (a sum, a filter, a comparison) reintroduces the precision loss the
assignment is testing for. A string that is never coerced is the only way to
guarantee `45,20` and `7800,00` survive.

**Throwing on the malformed record instead of collecting it in `rejected`.**
Rejected — a thrown exception on one bad line loses every valid record after
it in the same run, which is a worse failure than the one the malformed
line itself represents.

**Asking the upstream system for a JSON or API export instead of parsing this
file at all.** The most honest alternative, and the one worth naming: this
format exists because nobody owns it enough to change it, and a fixed-width,
mixed-encoding text dump run once a day is what happens when an integration
has no maintainer with the authority to fix it. Not viable for this
assignment — there's no upstream to ask — but it's the real answer to "what
would you build instead if you ran this for five years": push for a
contract (even a documented CSV/JSON schema) rather than re-deriving the
column layout every time the export quietly changes.

## Consequences

Easier: adding a new fixed-width field only means adding one entry to
`ORDER_LAYOUT` and one line in `ingest()` — the column positions are declared
in one place, not scattered across regexes or string indices.

Harder, and this is the real cost: the column layout is implicit contract,
not enforced anywhere except by `ORDER_LINE_LENGTH`. If the upstream system
inserts a field in the middle of the record without changing the total line
length, every field after the insertion point silently shifts and gets
misread — and because the line is still 77 characters, `ingest()` would
accept it as valid and produce wrong data with no rejection at all. This is
the same failure mode as the encoding bug the assignment opens with, just one
layer further in: passing the *shape* check is not the same as being
correct.

Two more concrete breaking points, both silent rather than crashing:

- A `customerName` longer than 32 characters gets truncated by the fixed
  column width with no warning — the export format itself has no way to
  signal overflow.
- If someone "fixes" the mismatched encodings upstream by re-exporting the
  order file as UTF-8 without telling anyone, `decodeOrderFile` would decode
  it as CP1257 anyway and corrupt the (now-correct) bytes — exactly the
  inverse of today's bug, and just as invisible in the output.

The cost accepted here is that this ingester trusts its config
(`ORDER_LAYOUT`, the encoding label) completely and has no way to detect that
the upstream format itself has drifted. A five-year version of this needs a
schema-version marker or a checksum on the column layout, not just careful
parsing of one snapshot of the format.
