# ADR-005 - Contract first, then a sequential saga that rolls back

**Status:** accepted
**Date:** 2026-10-26

## Context

The scaffold answered every checkout with 422 `not_implemented`, and every repeated key with 409. So I had to build the saga and decide what a repeated key gets back.

Shipping and notification have no undo call. Only inventory and payment can be rolled back, and that shaped the whole rollback design. The Spectral rules also made me decide things early. Every array needs `maxItems`, so I picked 20 items and a trace of 6 before writing any code.

## Decision

- **Contract first.** I committed and linted `openapi.yaml` before touching `orchestrator/src/`. `MAX_ITEMS = 20` in the code matches `maxItems: 20` in the contract.
- **One step at a time.** The saga calls payment, inventory, shipping, notification with `await`, so each step starts only after the last one succeeded.
- **Money in cents.** `priceToCents` and `centsToAmount` add whole cents and format once. A float turns 18.90 into 1889.9999999999998.
- **Timeout or failure.** `runStep` aborts a call after `REQUEST_TIMEOUT_MS`. That is a `timeout` and returns 504. A non-2xx answer is `failed` and keeps the mock's own code.
- **Rollback.** After a failure I release inventory, then refund payment, but only for steps that had finished. If a rollback call fails, the answer is 422 `compensation_failed`.
- **Idempotency.** The key is checked and marked `in_progress` with no `await` in between. A different body gets 409 mismatch, a request during the first gets 409 conflict, and a finished one replays the stored answer. The store files are re-read before every write.

## Alternatives considered

- **Parallel calls:** faster, but a declined payment would already have reserved stock. The README forbids it too.
- **Undo calls for shipping and notification:** would make rollback complete, but I can't change the mock services.
- **Events like PA5:** no single place knows if the order worked, and the caller gets no result. Checkout needs one answer, so I used orchestration.

## Consequences

The contract, the code and the trace agree, and a failure can be read step by step. Costs I accepted:

- If the orchestrator dies mid-saga, its `in_progress` record stays, and that key gets 409 forever.
- Shipping and notification can't be undone, so a late failure leaves a shipment behind.
- Sagas are stored by `orderId`, so two keys for the same order overwrite each other.
- The JSON files have no locking, so a second replica would break them.
- A fifth step means editing the step list, the rollback code and the trace limit by hand.
