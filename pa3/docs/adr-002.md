# ADR-002 — Idle timeout aggregation with in-memory state

**Status:** accepted
**Date:** 2026-09-24

## Context

Once the splitter breaks an order into separate item messages, each one goes through its own worker and comes back on `orders.results` in whatever order, or sometimes not at all. So the aggregator has to work out which results belong together, when an order is done, and what to do if a worker never answers or the same result shows up twice.

The assignment already fixed the mechanism (an idle timeout that resets on each result), so the parts I actually had to decide were the timeout number, what a partial result should contain, and how to deal with duplicates.

## Decision

- **Correlation.** Every item message carries `orderId`, `correlationId` (same value), `itemIndex` and `totalItems`, and the workers pass them through on the result. The aggregator groups by `orderId`. If a worker dropped or renamed one of these, the aggregator would log the result as malformed, ack it and throw it away, so that item would end up in `missingItemIndexes`.
- **State.** `in_flight` is a dict of `orderId -> {totalItems, items, correlationId, lastActivity}` behind one `threading.Lock`. `items` is keyed by `itemIndex`.
- **Duplicates.** Because `items` is keyed by `itemIndex`, a redelivered result just overwrites its own slot, so the count can't go up twice. I didn't need any extra code for that.
- **Timeout.** Every result resets `lastActivity` in `aggregate_result`. A background thread (`sweep_timeouts`) checks once a second and publishes a partial for any order that has been quiet longer than `AGGREGATOR_IDLE_TIMEOUT_SECONDS`. The tests use 5s. For production I'd probably start around 30s, but that's a guess. To pick it properly I'd measure how long each worker type takes (the physical one especially) and set the timeout to a few times the slowest normal case.
- **What a partial contains.** `status: "partial"`, the results received so far, `receivedItems`, and `missingItemIndexes` with the exact items that never came back. Whoever reads `orders.complete` can then retry or refund those items instead of only knowing that something went wrong.
- **One message per order.** I keep a `completed` set of orderIds that were already published (complete or partial). If a late duplicate or straggler arrives after that, it's ignored. I only noticed this problem when re-reading my code: without the set, a duplicate after completion recreated the order and the sweeper later sent a fake partial. The tests don't cover it.
- **Locking.** State changes happen inside the lock and publishing happens after it's released, so one slow publish doesn't block other orders.

## Alternatives considered

- **Fixed deadline from when the order starts.** I rejected this because it doesn't scale with order size. A deadline that works for 3 items would cut off a 50-item order that is still making progress. An idle timeout only fires when things go quiet.
- **Redis for the state.** It would survive restarts and allow more than one aggregator. I skipped it because it adds another service to run, and a dict with a lock is enough for one aggregator at this scale.
- **Letting RabbitMQ handle duplicates.** The broker redelivers unacked messages on purpose and can't tell that two messages are the same item, so it made more sense to dedupe on `itemIndex` myself.

## Consequences

- Completion is a simple `len(items) >= totalItems` check, and partials say exactly what's missing.
- If the aggregator restarts mid-order, `in_flight` and `completed` are lost. Results that were already acked are gone, so that order never gets a message. After a restart, a redelivered result for an already-finished order would also start a new entry that eventually times out as a partial. Storing the state in Redis or a database would fix that.
- State is only created when the first result arrives. If no worker answers any item of an order, the aggregator never hears about it and never sends a partial. Fixing that would need the router to tell the aggregator when it splits an order, and I didn't do that.
- `completed` grows forever. That's fine here, but with much more traffic, or orders with 500 items, I'd expire old entries after a TTL.
- With a single consumer and `prefetch_count=1`, throughput is limited. Scaling out would need the shared state mentioned above.
- I haven't load-tested this, so 5s works for the tests but the production number is still an estimate.
