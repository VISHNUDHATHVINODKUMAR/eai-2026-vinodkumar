# ADR-003 — Turning three different order formats into one shape

**Status:** accepted
**Date:** 2026-10-03

## Context

I got three orders that are really the same thing (same customer, same
items) but each system writes it down differently.

* **Web** sends normal nested JSON. It's already close to what I need.
* **Mobile** sends flat JSON with short field names like `oid`, `cust\_name`,
`cur`. The address is just one string:
`"Brīvības iela 100, Rīga, LV-1001, LV"` — I had to split it myself. The
date is a Unix timestamp in **seconds**, not milliseconds, so I had to
multiply by 1000 before using it. Currency and status are just numbers
(`978`, `1`) that mean nothing without a lookup table.
* **B2B** sends XML, and the file says `encoding="windows-1257"` at the top.
That's not a joke — if I read the file as normal UTF-8 text, the Latvian
letters (like in "Bērziņa") turn into garbled question marks, with no
error at all. It just quietly breaks. I had to decode the raw bytes with
the right encoding *before* parsing the XML.
* B2B also has a `<UnitListPrice>` field with a price in it. It looks
useful but it's not the real price — it's an old price written in comma
style (`24,99`). I'm not supposed to use it.

None of the three tells me the real price. For that I have to call a
separate pricing API, and that API can fail — it can say "I don't know that
product" (404) or just be down (500). I have to handle both without
crashing.

All three also carry payment info (a card number or a bank IBAN) that I'm
not allowed to keep. The schema I'm writing to doesn't even have a field for
it.

## Decision

I wrote one function per source (`translateWeb`, `translateMobile`,
`translateB2B`). Each one does the same four things:

1. **Read the file and pull out the fields I need.**
2. **Fix each product id** so it matches the pricing API's format
(`PROD-001`). Web ids are already fine, mobile ids just need `PROD-`
added in front, and B2B ids need the `SKU-` part removed from the front.
3. **Call the pricing API** for each item and use whatever it says for
price, currency, and tax. I never type a price into my own code. If an
item's id isn't found, or the API breaks, I don't crash — I skip that
one item and add a note about it to a `warnings` list instead. The rest
of the order still goes through.
4. **Build the final object**, copying over only the fields the schema
wants. I simply never read the payment fields into the output, so
there's nothing to accidentally leak.

A couple of smaller things I had to get right:

* **Prices as text, not numbers.** The schema wants `"24.99"` as a string,
always with two decimal places. I format it with `.toFixed(2)`, once,
right after the API gives me the number. I don't touch it again after
that — doing it twice is actually how you lose a decimal by accident.
* **Dates.** Even though web and B2B already look like proper dates, I
still run them through `new Date(x).toISOString()`. That's because
"looks right" isn't the same as "is formatted exactly the same way" —
this makes sure all three sources end up with the exact same date text
for the same moment in time.
* **The XML encoding.** I read the B2B file as raw bytes (not as text), and
only decode it to text myself using `TextDecoder("windows-1257")`. If I
let anything read it as UTF-8 first, the names would already be broken by
the time I got to them.

## Alternatives considered

For currency and status codes I don't recognize, I thought about just
letting the weird number through as text instead of stopping with an error.
I decided not to, because currency/status apply to the *whole order*, not
just one item. If I don't understand what currency something is, I don't
think it's safe to guess and quietly move on — better to stop and show a
clear error than save something wrong.

I also thought about using the pricing API's product name instead of the
name from the original order. I kept the order's own name instead, because
that's what the customer actually typed/saw when they ordered — the pricing
system's name is just for pricing, not for display.

## Consequences

Because I skip bad items instead of failing the whole order, it's possible
to end up with an order that has fewer items than it started with, and the
only place that shows up is the `warnings` list. If someone only looks at
the final order and ignores warnings, they could miss that something was
dropped.

Because I throw an error on an unknown currency or status code, one weird
value can stop that entire order from processing — there's no partial
result for that case, unlike missing products. I think that's the safer
choice for now, but it is inconsistent: products fail gently, currency and
status fail hard.

If a new source shows up later with yet another id format, I'd just add one
more case to my id-fixing function — that part's easy. But if the schema
itself ever changes (new required field), every one of my three functions
would break at once, since the schema doesn't allow extra or missing
fields. That's expected and kind of the point of having one shared schema,
but it does mean one schema change touches all three translators, not just
one.
