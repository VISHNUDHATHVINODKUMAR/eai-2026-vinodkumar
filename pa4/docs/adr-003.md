# ADR-003 — Map three order formats to one canonical order, priced from the pricing API



**Status:** accepted

**Date:** 2026-10-03



## Context



Web, mobile and B2B describe the same order in three different ways.



* **Mobile** uses flat JSON (`oid`, `cust_name`, `cur`). The address is one string, `"Brīvības iela 100, Rīga, LV-1001, LV"`, so `parseMobileAddress` splits it. The date `ts` is a Unix timestamp in seconds. Used as milliseconds it lands in January 1970, so `epochSecondsToIso` multiplies by 1000. Currency (`978`) and status (`1`) are bare numbers that need lookup tables.

* **B2B** is XML that declares `encoding="windows-1257"`. Read as UTF-8, `Bērziņa` becomes `B?rzi?a` and nothing throws an error. `decodeB2BXmlBytes` decodes the raw bytes first. With a single `<LineItem>`, fast-xml-parser gives an object, not an array, so `translateB2B` wraps it.

* B2B also has `<UnitListPrice>` (`24,99`). It is not the real price, so I never read it.



No source has the real price. I get it from the pricing API. It can have no entry for a product id, and it can be unreachable. With the service stopped, my calls failed before any response arrived, and the warning said `HTTP 0`. I must survive both cases.



Each source hides payment data in a different place. Web nests it in `customer.payment` (`method`, `cardHolder`, `cardNumber`, `expiryMonth`, `expiryYear`). Mobile has flat fields `pm`, `pan` and `pexp`. B2B has `<PaymentDetails method="wire">` with `<IBAN>` and `<BIC>`. The canonical schema has no field for any of it.



## Decision



One function per source: `translateWeb`, `translateMobile`, `translateB2B`. Each reads its file, fixes the product ids, prices the items and builds the canonical order.



* **Product ids.** `normalizeProductId` turns each source's id into the pricing API's `PROD-001` format.

* **Pricing.** `enrichFromPricing` calls the API for one item. `enrichItems` loops over the order. No price is typed into my code.

* **Money.** `toDecimalAmount` turns the API's number into a string with two decimals, so `4.5` becomes `"4.50"`. I convert once, at the end. A JavaScript number would print `4.5`.

* **Items that cannot be priced.** An unknown product id gives an `UNKNOWN_PRODUCT` warning. A failed API call gives a `PRICING_API_ERROR` warning. Each warning names the product. I drop that item and price the others. In my test, `PROD-999` was dropped and `PROD-001` came out as `"22.50"`. With the service stopped, no item could be priced, so `order` was `null` and only the warnings remained. No item ever gets `0.00`, because a fake price looks like a real one.

* **Payment data.** I never read `customer.payment`, `pm`/`pan`/`pexp` or `<PaymentDetails>`. There is no filter function. The fields are simply never copied.



## Alternatives considered



**Fail the whole order when one item cannot be priced.** I rejected it. One unknown product would block an order that is otherwise fine. The cost of my choice is that an order can leave with fewer items than it came in with.



**Pass unknown currency or status codes through as text.** I rejected it too. They describe the whole order, and a wrong currency is worse than no order. `mapCurrencyCode` and the status mappers throw instead. The cost is that one odd code stops the whole order.



## Consequences



**Easier:** one schema and one set of tests cover all three sources. A fourth source with a new id format needs one more case in `normalizeProductId`.



**Harder:** if the canonical schema gains a required field next semester, all three translators break at once. I do not own the schema, so I would edit three functions.



**What breaks first:** a dropped item. The only trace is the warning, so someone who reads only the final order would not notice. If the pricing service is down, the whole order is lost and only warnings survive. I accept both costs.



**Inconsistency I accept:** missing products fail softly, but unknown currency and status fail hard. Order-level errors are not safe to guess.
